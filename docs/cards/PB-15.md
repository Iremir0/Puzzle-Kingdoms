# PB-15 Phone performance and layout

Owner: — (suggested Emir) · Milestone: M6 · Size: L · Branch: `feature/PB-15-phone-perf-layout` ·
Replaces: M6-01, M6-02 · Needs: PB-1, best after PB-11/PB-12

## Why
Mobile players drop a game that stutters, drains the battery or hides buttons
under the notch. Budget phones are most of the market; the game must run there,
not only on the developer's phone.

## Today
- PB-1 notes: first device, first problems.
- UI is uGUI built from code with anchors in screen fractions (`Ui.cs`); no
  safe-area handling.
- Procedural sprites (gems, silhouettes) are generated at start-up; cost unknown.

## Build
1. **Target devices:** one mid-range (the PB-1 phone) and one low-end (2-3 GB
   RAM, a 3-4 year old phone). Targets: 60 fps puzzle, 30+ fps battle, start-up
   under 5 s, no frame over 50 ms in normal play.
2. **Profile:** dev build with *Autoconnect Profiler*; record a full stage
   (puzzle → camp → battle). Look at CPU main thread, GC allocations per frame,
   GPU (overdraw on the battle).
3. **Fix the top 3 hotspots** you find. Usual suspects: allocating every frame
   (LINQ, string formatting in `Update`), rebuilding whole UI lists on every
   change, too many canvases being rebuilt, particles overdraw, shadows.
   Each fix: before/after numbers in Notes.
4. **Safe area:** a `SafeArea` component that fits a root `RectTransform` to
   `Screen.safeArea`; all screens live under it.
5. **Aspect ratios:** check 16:9, 19.5:9, 20:9 and a tablet 4:3. Use the
   Device Simulator. Fix overlaps; avoid fixed pixel sizes.
6. **Battery/heat:** cap frame rate at 60 (`Application.targetFrameRate`),
   30 on menus if it helps.

  development build running, choose the device in the *Play Mode* dropdown at the

  dropdown) and pick phones; it shows notches and safe areas.

## Notes
_Findings, screenshots, numbers, decisions taken while working on this card._

**2026-11-20 (Emir, without a phone).** Fixed what the code review found before profiling:
- Safe area: `Views/Common/SafeArea.cs` fits a `SafeArea` rect under the canvas to `Screen.safeArea`; every
  screen is built under it (`GameApp`, `Ui.CreateSafeArea`). Backgrounds (`Ui.Backdrop`) and pop-up shades
  (`Ui.Shade`: Settings, Consent, Cloud conflict) carry `FullBleed` and still reach the screen edges.
  The tutorial shades stay inside the safe area (a thin undimmed strip behind the notch; fine for now).
- Battle effects: puffs, coins, arrows and orbs are pooled and share one material per colour; before, every
  bit was a new primitive with its own material copy that was never freed. `UnitActor` writes the flash colour
  only when it changes and frees its material copies when the battle closes.
- `BattleSimulator.Step(List<BattleEvent>)` and `BattleReplay.Advance(sim, list)` fill a reused list; the battle
  screen no longer allocates a list per tick. Tests: `StepIntoABufferGivesTheSameEventsAsStep`,
  `AdvanceIntoABufferPlaysTheSameBattle`.
- Puzzle hint: when no move exists the board scan runs once a second, not every frame.
No before/after numbers yet: they need the phone profile (steps 1-3).
